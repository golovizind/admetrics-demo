# Admetrics

Учёт аккаунтов и финансовых потоков команды маркетологов, работающих с Facebook.
Собирает данные напрямую через мультитокен (тот же контейнер сессии, что отдаёт
FBTOOL), ведёт реестр активов и считает витрину: **маркетолог → цикл → гео**.
Отдельно сверяет открут FB с реальными списаниями по картам MyBroCards.

Интерфейс — Telegram Mini App и тот же портал в браузере (единый SPA). Уведомления
шлёт Telegram-бот.

> **Демо-версия.** Ключи, адреса и данные реальной команды удалены. Обзор проекта
> со скриншотами — [docs/admetrics-demo.pdf](docs/admetrics-demo.pdf). Запустить
> панель локально на вымышленных данных (6 маркетологов, 17 кабинетов, 50 дней
> истории) — одной командой, нужен Python 3.10+:
>
> ```bash
> ./run_demo.sh        # → http://127.0.0.1:8080, вход админом без Telegram
> ```
>
> Данные генерирует [demo_seed.py](demo_seed.py). Токены и прокси в демо фиктивные,
> поэтому «Собрать сейчас» и кнопки управления кампаниями ответят ошибкой доступа —
> всё остальное работает на сгенерированных данных.

Базовая валюта — **доллар (USD)**; переключается через `ADMETRICS_BASE_CURRENCY`.
Циклы залива — недели пн–вс со сквозной нумерацией (якорь: 2026-08-03 = цикл 239).

## Три слоя данных

**Доступы.** `marketers` → `identities` (ФБ-личка = один мультитокен) →
`identity_status_log`. У маркетолога личек много; форма их добавляет,
а не перезаписывает.

**Активы.** `businesses`, `ad_accounts`, `ad_account_owner`,
`ad_account_access`, `ad_account_snapshots`, `cards`. Кабинет попадает
в реестр фактом существования, а не фактом трат: забаненный до открута
кабинет — тоже актив.

**Факты.** `spend_daily` (авторитетный итог по кабинету за день),
`spend_country_daily` (детализация по фактической доставке),
`spend_campaign_daily`, `ad_daily`, `fb_transactions`, `card_payments`,
`fx_rates`.

## Три принципа, на которых держится корректность

**Владелец не входит в первичный ключ факта.** Спенд кабинета за день —
объективное число и не зависит от того, чей токен его прочитал. Атрибуция
живёт в `ad_account_owner` интервалами с историей, поэтому передача кабинета
в середине цикла делит спенд между старым и новым владельцем правильно.
Если положить владельца в ключ, шаренный кабинет соберётся дважды и итог
по команде удвоится.

**Итоги считаются от маркетолога, а не от гео.** Субъект отчёта — маркетолог,
поэтому суммы берутся из `spend_daily`. Гео из `breakdowns=country` только
детализирует и не может испортить итог: если разбивка Meta не сходится
с итогом кабинета, разница показывается строкой «—», а расхождение попадает
в `geo_gaps`.

**Отсутствие данных не молчит.** Нет курса → сумма не занижается нулём, пара
валюта/дата попадает в `missing_rates`. Нет формального владельца → берётся
эффективный (через доступ личек), а совсем без него спенд собирается в группу
«Без владельца» плюс отдельный список сирот. Деньги считаются в `Decimal`:
сверка с картами идёт до цента.

## Токены живут долго: обновление из сессии

Мультитокен Ads Manager протухает за часы — но протухает только сам токен,
а куки сессии живут месяцами. В базе лежит снапшот контейнера `{cookies, ua,
token}`; свежий рабочий токен всегда есть в живой сессии.

Поэтому перед каждым сбором коллектор для каждой лички достаёт свежий токен из
её же сессии (`graph.refresh_container`) и молча переписывает контейнер
(`store.update_identity_token`, не трогая статус и `connected_at`). Токен и
его куки валидны только вместе — токен в одиночку Meta не принимает, — поэтому
обновляется именно контейнер целиком. Это убрало вечное «нет доступа —
переподключить токен» на ровном месте.

## Сверка с MyBroCards и автоистория

Вторая половина учёта — реальные списания по картам. `collect_cards` тянет
платежи MyBroCards и сверяет с открутом FB. Владелец карты берётся из самого
платежа (email + имя пользователя), а не по last4 — четырёх цифр на тысячи
карт не хватает.

Обычное окно узкое (45 дней): финальный статус платежа приходит часами позже,
pending уходит в declined — один раз собрать нельзя. Но «за всё время» должно
быть за всё время, поэтому история дотягивается сама: каждый прогон подтягивает
один кусок (`CARDS_BACKFILL_CHUNK_DAYS`, по умолчанию 90 дней) старее уже
собранного и двигает метку в `app_kv` назад, пока не упрётся в пол-дату
(`CARDS_HISTORY_FLOOR`, по умолчанию `2023-01-01`). Дальше метка стоит, лишних
запросов нет. Никакого ручного скрипта: догоняется за несколько циклов сбора.

## Доступ и роли

Вход — через Telegram (бот `/start` или кнопка входа на портале). Внутри Mini App
подпись едет заголовком, в браузере — подписанной кукой сессии. Админ — тот, чей
Telegram-id указан в `ADMIN_TG_IDS`; у него полная витрина и управление, у
маркетолога — только свои лички, кабинеты и платежи.

Аватарки профилей подтягиваются из Telegram (`/api/avatar/...`, кэш на сутки);
у непривязанных к TG остаётся заглушка-кружок.

### Лички: одинаковые права у обеих ролей

Мультитокены протухают часто, поэтому заводить и менять их умеют оба:

| Действие | Маркетолог | Админ (через «Людей») |
|---|---|---|
| Добавить личку | свою | любому маркетологу |
| Выключить / включить | свою | любую |
| Отозвать секрет | свою | любую |
| Видеть список | только свои | все, с именем владельца |

Маркетолог ограничен своими личками на сервере, а не в вёрстке: `identity_id`
приходит из формы, поэтому каждое действие проверяет владение и отвечает 403
на чужую личку.

**Выключение и отзыв — не удаление.** Выключенную личку коллектор пропускает,
но её можно вернуть. Отзыв стирает мультитокен и прокси, а сама запись и
история остаются: связь «эта личка видела такие-то кабинеты» нужна для учёта
активов и после того, как доступ отобрали.

## Запуск локально

```bash
pip install -r requirements.txt

export ADMETRICS_KEY="$(python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())')"
export TELEGRAM_BOT_TOKEN=…  ADMIN_TG_IDS=123456789
export MYBROCARD_API_KEY=…            # сверка с картами; без него карты пропускаются
export ADMETRICS_BASE_CURRENCY=USD    # базовая валюта витрины

python3 manage.py init
python3 manage.py marketer add "Анна" --login anna@team.pro   # почта = ключ к картам
python3 manage.py identity add anna --file token.txt --proxy socks5h://user:pass@host:port
python3 collector.py --registry-only                          # проверить, что токен живой
python3 manage.py owner set act_123456 anna                   # назначить владельца
python3 manage.py fx set 2026-08-12 THB 0.031                 # курс к базовой валюте на дату
python3 collector.py                                          # сбор за скользящее окно

python3 webapp.py --port 8080          # портал; --tunnel поднимет HTTPS через cloudflared
python3 bot.py                         # бот: вход и уведомления
```

Прокси задавайте `socks5h://` (DNS решает прокси, не клиент): сервер ходит в Meta
только через прокси лички, а `socks5://` резолвит имя локально и на сервере падает.

## Отчёт и проверки в терминале

```bash
python3 manage.py report --cycle 240      # витрина маркетолог → цикл → гео
python3 manage.py report --last 3         # последние три цикла
python3 manage.py accounts --problem      # кабинеты не в статусе ACTIVE
python3 manage.py owner orphans           # спенд без владельца
python3 manage.py check                   # проверки целостности
```

`manage.py check` ловит то, что ломается молча: пересечение интервалов владения
(завышает спенд), кабинеты со спендом без владельца, дырки в курсах, лички,
требующие переподключения.

## Разведка перед подключением

Перед тем как заводить личку в систему, полезно посмотреть, что этот конкретный
мультитокен вообще отдаёт — набор полей зависит от версии API, приложения токена
и уровня доверия аккаунта:

```bash
python3 probe.py --session "<контейнер FBTOOL>" --proxy socks5h://… --max-accounts 10
```

Скрипт только читает, ничего не меняет в Meta и не пишет в базу.

## Сбор по расписанию

Веб поднимает внутренний планировщик; для продакшна лучше внешний cron:

```cron
30 6 * * *   cd /opt/admetrics && set -a && . ./.env && set +a && python3 collector.py --days 7
30 5 * * 1   cd /opt/admetrics && set -a && . ./.env && set +a && python3 collector.py --days 28
```

Окно скользящее: Meta уточняет цифры прошедших дней около месяца, поэтому
собирать день один раз нельзя. Историю карт при этом тянуть каждый прогон не
нужно — она дотягивается сама (см. «Автоистория»).

## Выкатка на сервер

Код живёт в `https://gitlab.example.com/demo/admetrics`. Обновление —
одна команда **с Mac из папки проекта** (не из облачного Cowork: git не может
коммитить на примонтированной папке, а до сервера из облака нет сети):

```bash
./release.sh "что поменяли"
```

Она коммитит изменения, пушит в GitLab, отправляет на сервер содержимое ровно
этого коммита (`git archive "$SHA" | ssh | tar` — сервер этот способ переносит
стабильнее, чем `git fetch`) и запускает `deploy.sh`, который перезапускает бот
с панелью. Что именно выкачено, лежит на сервере в `/opt/admetrics/.deployed-commit`.

Если GitLab недоступен (он изредка рвёт соединение), скрипт скажет об этом и
остановится. Выкатить всё равно — `FORCE=1 ./release.sh`, а `git push origin
main` повторить позже. Оставшийся `.git/index.lock` от прерванной попытки
снимается `rm -f .git/index.lock`.

База на сервере при выкатке не трогается: она не в репозитории. `.env` тоже
остаётся на месте — когда поменяется, отправить отдельно:

```bash
scp .env root@СЕРВЕР:/opt/admetrics/.env && ssh root@СЕРВЕР chmod 600 /opt/admetrics/.env
```

`migrate.sh` нужен только для переезда на новый сервер и переноса базы
(`WITH_DB=1`), для обновлений — нет.

## Защита данных

- **Пароль маркетолога хешируется** (pbkdf2, 200k итераций) — вернуть исходное
  значение нельзя и не нужно.
- **Мультитокен и прокси шифруются** (Fernet, обратимо) — коллектору нужен живой
  токен, чтобы ходить в Meta.
- Токены и контейнеры сессий — как пароли: в логи и в текст ошибок не попадают
  (редактируются), в чат и наружу не отдаются.

`ADMETRICS_KEY` держать в секрет-менеджере отдельно от базы. Сервис — за VPN
или reverse-proxy с TLS.
